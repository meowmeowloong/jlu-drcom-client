# 吉大校园网「不限设备数量」路由器方案：操作指南与原理解析

> **一句话结论**：把 DrCOM 认证从"每台手机/电脑各自登录"搬到一个路由器上，让路由器替你完成认证和保活，然后靠 **NAT** 让后面挂的无数台设备共享这一个会话——学校眼里你只有"一台设备"，自然就没有设备数量限制了。
>
> **适用场景**：吉大宿舍，墙上网口接路由器（红米 AX3000 等），希望全屋设备免认证上网。
> **硬约束**：不刷第三方固件，保留原厂 MiWiFi，仅通过开启 SSH 塞入一个静态编译的认证客户端。

## 一、结论先行

| 问题 | 答案 |
|---|---|
| 学校为什么"限制设备"？ | 不是真的数你有几台设备，而是**一个账号同一时间只允许一个会话**，会话绑定在"认证的那块网卡（MAC）"上。换设备登录会踢掉上一个。 |
| 怎么绕过去？ | 让**路由器**去做那个"唯一登录的设备"。手机、电脑、平板都连路由器的 WiFi/网口，它们的流量被 NAT 伪装成路由器的流量。 |
| 需要刷机吗？ | 不需要。原厂 MiWiFi 开 SSH，塞一个**静态编译的 32 位 ARM 二进制**即可。 |
| 需要电脑常开吗？ | 不需要。客户端跑在路由器里，开机自启 + 崩溃自动拉起，7×24 保活。 |
| 最大坑是什么？ | **电脑上还开着旧的 DrCOM 客户端**，和路由器抢同一个会话，互相踢，表现为"每 23 秒登录成功→超时→重登"。退掉电脑客户端即可。 |

## 二、操作指南

### 2.1 前提条件

- 一台**可开启 SSH** 的路由器（本方案实测：红米 AX3000 RA81，高通 IPQ5018）。
- 一个能 SSH 的电脑（Windows 自带 OpenSSH 需 `ssh-rsa` 兼容参数，见下文）。
- 你已知的 DrCOM 账号参数：`server`、`username`、`password`、`mac`。

> 关于红米 AX3000 的一个重要实测结论：它的 SoC 虽然是 64 位的 IPQ5018，但**原厂固件的用户态是 32 位 ARMv7（软浮点 ABI）**。所以必须编 32 位软浮点二进制，编 aarch64 会 `Exec format error`。

### 2.2 获取认证参数

从你电脑上**能正常登录的原客户端**里抄出参数（本仓库的 Qt 客户端在 `Login.ini`，或安卓版配置里），依次是：

```
server   10.100.61.3        # DrCOM 服务器地址（内网）
username your_account       # 你的学号/账号
password ********           # 你的密码
mac      11:22:33:44:55:66  # 账号绑定的 MAC —— 必须等于路由器 WAN 口 MAC
host_name JLU-DrCOM         # 主机名（可随便填）
```

> **MAC 是关键**：学校把"设备"定义成"一块网卡"。账号绑定的 MAC 必须和路由器 **WAN 口（eth0）** 的 MAC 一致。红米 AX3000 可以在 MiWiFi 后台把 WAN 口 MAC 克隆成账号绑定的 MAC，对上即可。

### 2.3 开启路由器 SSH

用社区工具 **XMiR-Patcher** 开启 SSH（这一步需在联网状态下按工具提示操作，不同小米固件版本略有差异）。开启后路由器上会跑一个 **dropbear** SSH 服务。

> dropbear 只支持老旧的 `ssh-rsa` 主机密钥，新版 OpenSSH 默认禁用了它，所以直连会报
> `no matching host key type found. Their offer: ssh-rsa`。解决方式见下一条命令里的兼容参数。

### 2.4 交叉编译客户端（在 WSL / Linux 里）

Windows 的 Git Bash 跑不了 Linux 交叉工具链，必须进 **WSL**：

```bash
# 下载 musl 静态交叉工具链（针对 32 位 ARM 软浮点）
curl -O https://musl.cc/arm-linux-musleabi-cross.tgz
tar xzf arm-linux-musleabi-cross.tgz
export PATH=$HOME/arm-linux-musleabi-cross/bin:$PATH

# 编译（本仓库已写好脚本）
sh scripts/build.sh        # 产出 bin/jlu-drcom-armv7
```

关键编译参数：`-static -no-pie`（完全静态、非 PIE，兼容老内核 Linux 4.4）。产物验证：

```bash
readelf -h bin/jlu-drcom-armv7 | grep -E "Class|Machine|Flags"
# 应看到: Class: ELF32 / Machine: ARM / Flags: 0x5000200 (Version5 EABI, soft-float ABI)
```

### 2.5 传文件到路由器

需要传三样：二进制 `jlu-drcom-armv7`、配置 `drcom.conf`、脚本 `drcom-service.sh` 和 `install.sh`。

```bash
# 传文件（scp -O 强制走老 SCP 协议，dropbear 不一定支持 SFTP）
scp -O bin/jlu-drcom-armv7 etc/drcom.conf \
      scripts/drcom-service.sh scripts/install.sh \
      root@192.168.31.1:/tmp/drcom/
```

### 2.6 在路由器上安装

SSH 连上路由器（注意下面这串 `-o` 参数是 dropbear 兼容所必需的），然后执行安装脚本：

```bash
# 一条能连上 dropbear 的 ssh 命令（密码认证，非交互可用 SSH_ASKPASS 辅助）
ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
    -o PreferredAuthentications=password -o PubkeyAuthentication=no \
    -o HostKeyAlgorithms=+ssh-rsa -o PubkeyAcceptedAlgorithms=+ssh-rsa \
    -o KexAlgorithms=+diffie-hellman-group14-sha1,diffie-hellman-group1-sha1 \
    -o Ciphers=+aes128-cbc,3des-cbc -o MACs=+hmac-sha1 \
    root@192.168.31.1

# 路由器上执行：
sh /tmp/drcom/install.sh
```

安装脚本会自动做五件事：

1. 二进制装到 `/data/drcom/drcom`（`/data` 分区重启不丢）；
2. 配置装到 `/etc/drcom.conf`；
3. 服务脚本装到 `/data/drcom/drcom-service.sh`；
4. 写**开机自启**（`/etc/rc.local`）+ **崩溃守护**（crontab 每分钟 `sh $SERVICE start`）；
5. 立即启动。

### 2.7 验证

```bash
# 看状态
sh /data/drcom/drcom-service.sh status
# 实时看日志
tail -f /data/drcom/drcom.log
```

**判定标准**：日志里出现一次 `登录成功` 之后，**不再**反复出现 `keepalive_1 响应超时`，即为稳定接管。

> ⚠️ **务必退掉电脑上的旧客户端**（托盘图标右键退出，或任务管理器结束 `DrCOM_JLU_Qt.exe`），否则它和路由器抢同一个会话，日志会无限循环"登录成功→超时→重登"。

**验证外网时注意**：校园网通常**封 ICMP（ping）**，所以 `ping 8.8.8.8` 不通不代表没网。要用 TCP 验证：

```bash
wget -q -T 6 -O /dev/null http://www.baidu.com && echo 通了 || echo 不通
```

（本次实测：`ping` 100% 丢包，但 DNS 解析正常、HTTP 拉百度首页成功——即外网已通。）

## 三、原理解析（自顶向下）

> 这一节按 **Kurose & Ross《计算机网络：自顶向下方法》** 的层次，从上到下讲清楚：从"我想上网"这个应用需求，一路讲到物理层的比特流，每一层解决什么问题、在这个吉大方案里对应什么现象。

```
┌────────────────────────────────────────────────────────┐
│  应用层   DrCOM 客户端（登录/保活报文，挑战-应答）        │
├────────────────────────────────────────────────────────┤
│  传输层   UDP : 61440（无连接，应用层自己补可靠）        │
├────────────────────────────────────────────────────────┤
│  网络层   IP 寻址 / 默认路由 / NAT 改写源地址            │
├────────────────────────────────────────────────────────┤
│  链路层   以太网帧 / MAC 地址 / ARP（账号绑定 MAC）      │
├────────────────────────────────────────────────────────┤
│  物理层   网线(1000BASE-T) / WiFi(802.11) 的比特流      │
└────────────────────────────────────────────────────────┘
```

### 3.1 应用层：DrCOM 认证协议

**应用层回答的问题是**："两个应用程序之间，用什么报文格式、按什么顺序说话？" HTTP、SMTP、DNS 都是应用层协议；**DrCOM 也是一种应用层协议**，只不过它是为校园网认证这个特定任务设计的。

它的交互是一个**状态机**：

```
 客户端                              认证服务器(10.100.61.3)
   │  (1) challenge 请求/探测              │
   │ ───────────────────────────────────▶ │
   │  (2) 服务器回一个随机"挑战值"          │
   │ ◀─────────────────────────────────── │
   │  (3) login：账号 + 混淆后的密码        │
   │        + 基于挑战值算出的校验和         │
   │ ───────────────────────────────────▶ │
   │  (4) 校验通过 → "登录成功"             │
   │ ◀─────────────────────────────────── │
   │  (5) keepalive_1 / keepalive_2       │
   │      每 ~20 秒一轮，确认"还活着"        │
   │ ◀──────────────────────────────────▶ │
```

几个值得注意的点：

- **挑战值（challenge）是干嘛的？** 防重放。登录报文里的校验和把服务器刚发的随机挑战值也算进去了，所以别人抓包重放你上次的登录报文是没用的——挑战值已经变了。
- **密码不是明文吗？** DrCOM 用 `ror()` 循环移位对密码做了混淆，报文整体再用 MD5 生成校验和防篡改。**但这是轻量混淆，不是 TLS 级别的加密**——它是给可信校园内网用的老协议。所以密码别到处乱贴，本仓库的 `drcom.conf` 也已被 `.gitignore` 忽略。
- **为什么要保活（keepalive）？** 服务器的会话有超时机制，需要客户端周期性发心跳来"续命"；反过来，客户端也靠"心跳有没有回应"来判断自己是否还持有会话——**一旦服务器不回了，客户端就重新登录**（这就是日志里 `keepalive 中断，准备重新登录` 的出处）。

### 3.2 传输层：UDP 与端口 61440

**传输层回答的问题是**："数据到了目标主机之后，交给哪个进程？" IP 地址只能定位到主机，**端口号**才定位到进程。DrCOM 服务器就监听在 **UDP 61440** 端口上。

为什么 DrCOM 用 **UDP** 而不是 TCP？

| | TCP | UDP |
|---|---|---|
| 连接 | 需要三次握手，有连接状态 | 无连接 |
| 可靠性 | 自动重传、按序、流控 | 不保证，丢了就丢了 |
| 开销 | 高 | 低 |

DrCOM 的登录/保活是**短小的请求-响应**，而且协议自己定义了"超时重登"这套逻辑，正好补上了 UDP 缺失的可靠性——与其用 TCP 的握手和连接状态去伺候一个"每 20 秒说一句话"的协议，不如用 UDP 裸发、自己控制节奏。

**关键推论**：因为 UDP 不可靠，所以**客户端必须自己做超时与重试**。你会在日志里看到的 `keepalive_1 响应超时: Resource temporarily unavailable`，本质是客户端在非阻塞 socket 上 `recv()` 超时（`EAGAIN`），然后应用层决定"重新登录"。这就是"传输层欠的债，应用层来还"。

### 3.3 网络层：IP 寻址、DHCP、默认路由

**网络层回答的问题是**："数据怎么跨网段、跨路由送到目的地？" 靠的是 **IP 地址**和**路由表**。

把这个方案里涉及的网络层事实列出来：

1. **DHCP 拿地址**：路由器 WAN 口插上墙上网口后，通过 DHCP 从学校拿到 IP（校园网分配的 IP/掩码）、网关和 DNS（以学校实际分配为准）。

2. **默认路由**：路由器里有一条
   ```
   default via <校园网网关IP> dev eth0
   ```
   意思是"凡是不属于本地网段的包，都从 eth0 口交给网关"。

3. **认证前 vs 认证后，路由没变，变的是防火墙**：很多人以为"登录 = 拿到 IP / 建立路由"，其实不是。IP 和路由在认证前就有了。**认证的作用是让网关上的 ACL/防火墙把你这个 IP 从"只许访问认证服务器和 DNS"的白名单，升级成"允许访问整个互联网"**。所以"登录成功"本质是"网关把我放行了"。

4. **私有 IP vs 公网 IP**：LAN 侧（手机电脑）用的是 `192.168.31.x` 这类 **RFC1918 私有地址**，这些地址**不能在互联网上路由**。它们必须被转成 WAN 口那个公网地址才能出去——这就要靠下一节的主角 **NAT**。

### 3.4 链路层：MAC 地址、ARP、账号与 MAC 绑定

**链路层回答的问题是**："在同一个网段（同一根线/同一个交换机）里，帧怎么送到具体那块网卡？" 靠的是 **MAC 地址**——48 位，网卡出厂烧死，全球唯一。

- **IP vs MAC**：IP 是"你在网络里的**逻辑位置**"（会随网络变），MAC 是"你这块网卡的**物理身份**"（跟一辈子）。同一网段内靠 **ARP** 把 IP 解析成 MAC。

- **为什么账号要绑定 MAC？** 因为学校需要一个"这台设备就是你"的依据。登录一次绑定一个 MAC，之后这个账号的会话就认这个 MAC。

- **为什么本方案要求路由器 WAN 口 MAC 和账号绑定的 MAC 一致？** 因为路由器对外"露面"的就是 WAN 口（eth0）这块网卡。学校看到的是 WAN 口的 MAC。若不一致，服务器会认为"不是这台设备在登录"，认证过不去。红米 AX3000 可以在 MiWiFi 后台把 WAN 口 MAC 克隆成账号绑定的 MAC，对上即可。

### 3.5 贯穿层：NAT —— 「不限设备数量」的真正核心

> NAT 严格说是跨网络层和传输层的机制，但它是本方案**全部价值的来源**，单独拿出来讲。

**NAT（Network Address Translation，网络地址转换）**：路由器把内网设备发出去的包，源地址改写为自己 WAN 口的公网 IP，并记一张映射表；响应回来时，再按表把目标地址改回原内网设备。

更精确地说是 **NAPT（端口地址转换）**：不只看 IP，还改**端口号**。这张表长这样：

```
内网侧                         外网侧
192.168.31.5 : 54321   ⟷   49.x.x.x : 45678
192.168.31.7 : 54321   ⟷   49.x.x.x : 45679
192.168.31.9 : 8080    ⟷   49.x.x.x : 45680
...（成千上万条）
```

**靠端口号这个"第二维"**，一个公网 IP 就能同时承载整个宿舍成百上千个并发连接。

**为什么这能"解除设备数量限制"？** 看这条数据流：

```
 手机A (192.168.31.5) ─┐
 电脑B (192.168.31.7) ─┼─▶ [路由器 NAT] ─▶ 源IP统一变成 49.x.x.x（校园网分配的 IP） ─▶ 校园网关 ─▶ 互联网
 平板C (192.168.31.9) ─┘
```

学校认证的是**路由器这一台设备**。所有内网设备的流量，经过 NAT 后在外界看来都是"路由器这台设备发出来的"。学校根本不知道、也无法知道你后面挂了 3 台还是 30 台——**它只看到一台设备在正常上网**。这就是"不限设备数量"的物理原理。

**顺便解释我们踩过的坑——单会话冲突**：

DrCOM 的规则是"同一账号 + 同一 MAC，新登录会踢掉旧会话"。如果电脑上还开着旧的 Qt 客户端，它就也在用同一个账号、从同一个 WAN 口 MAC 出去认证。结果：

```
路由器客户端 登录成功 → 电脑客户端又登录 → 服务器把会话判给电脑 → 路由器保活被无视 →
路由器客户端 超时重登 → 又把会话抢回来 → 电脑客户端被踢 → …… 无限循环
```

表现在日志里就是每 ~23 秒一次 `登录成功 → keepalive 超时 → 重新登录`。**解法只有一个：退掉电脑客户端，让路由器独占这个会话。**（这也是为什么装好后，电脑上的 DrCOM 客户端应该关掉并取消开机自启。）

### 3.6 物理层（简述）

**物理层**只管一件事：**把 0/1 比特真正搬过去**，不关心 IP、账号、加密。

- 墙上网口 → 路由器 WAN 口：**网线**，千兆以太网（1000BASE-T），双绞线差分信号。
- 路由器 → 手机/电脑：**WiFi**（802.11ax/ac 无线电）。

它不参与"认证""NAT"这些逻辑，但一切上层都压在它上面——网线松了、WiFi 信号差，上层协议再正确也没用。

### 3.7 两个容易被忽略的横切知识点

- **DNS**：路由器内置 `dnsmasq`，做局域网 DNS 转发。内网设备把 DNS 配成路由器（`192.168.31.1`），路由器再向学校的 DNS 递归查询。所以你连上 WiFi 不需要手配 DNS。

- **ICMP 被墙**：很多校园网**禁止 ping（ICMP echo）**，理由是防扫描、防攻击。所以判断"有没有网"别用 ping，要用 TCP/HTTP（`wget` 拉个网页）。本次实测就是：ping 全丢，但网页秒开。

```
                 ┌──────────────────┴───────────────────────────┐

                    （这些设备不需要装任何认证客户端）
```

**一句话总结**：把"唯一合法登录的设备"这个身份，从你的手机/电脑转移到了路由器上；再用 NAT 把全屋设备都藏到路由器身后。学校能管住的那"一台设备"的会话，被路由器稳稳占住，于是后面设备数量对学校来说就不存在了。

## 五、常见问题与排错

| 现象 | 原因 | 解法 |
|---|---|---|
| `Exec format error` | 编了 aarch64，但路由器是 32 位 armv7 | 用 `build.sh` 默认的 armv7 软浮点重编 |
| `no matching host key type ... ssh-rsa` | dropbear 只认 ssh-rsa，新版 OpenSSH 禁了 | ssh 加 `-o HostKeyAlgorithms=+ssh-rsa` 等兼容参数 |
| `scp` 卡住/失败 | dropbear 不一定支持 SFTP | 用 `scp -O` 强制老协议 |
| 日志无限循环"登录成功→超时→重登" | **电脑客户端还在跑，抢会话** | 退掉电脑上的 DrCOM 客户端 |
| `ping` 不通但网页能开 | 校园网封 ICMP | 用 `wget`/浏览器验证，别信 ping |
| 路由器重启后不登录 | rc.local 没生效 / 配置丢了 | 确认 `/etc/drcom.conf` 存在、crontab 守护在跑 |
| 换宿舍/换账号后连不上 | server 或 MAC 变了 | 改 `/etc/drcom.conf`，`sh /data/drcom/drcom-service.sh restart` |
